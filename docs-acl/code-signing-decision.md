# 代码签名决策记录

日期：2026-10-26
状态：**决定不签名**（内测阶段）

## 背景

启动器分发时，Windows SmartScreen 会拦截未签名的可执行文件，提示「Windows 已保护你的电脑」。为消除此提示，评估了五条路径。

## SignPath Foundation 申请结果

2026-10-26 提交申请，同日收到拒绝信（Phillip Deng）。核心理由不是许可或合规问题，而是**公开可见度不足**。

信中列出的评估维度：

- GitHub 星标、fork、贡献者数量
- 外部文章与独立第三方提及（Reddit、Stack Overflow、YouTube）
- 机构背书
- 持续活动的证据

原文：`your project doesn't yet show enough of these signals`

结论：该计划面向「已成立的项目」，新 fork 在结构上无法满足。项目获得更广泛认知后可重新申请。

## 方案对比

| 方案 | 成本 | 实际效果 | 结论 |
| --- | --- | --- | --- |
| 不签名 | ¥0 | 提示「未知发布者」，点「更多信息 → 仍要运行」 | **当前采用** |
| 自签名证书 | ¥0 | 提示变为「发布者不受信任」，比不签更差；SmartScreen 仍拦截 | 否决 |
| Certum 开源证书（OV） | 约 €29/年 | 初期仍触发 SmartScreen，需累积下载量 | 备选 |
| Azure Trusted Signing | 约 $9.99/月 | 与 OV 类似，个人身份审核较严 | 备选 |
| EV 证书 | ¥2000+/年 | **唯一能立即消除警告**的证书类型 | 暂不考虑 |
| Microsoft Store 上架 | 约 $19 一次性 | Store 签名的包无警告，顺带有分发渠道 | 正式版可考虑 |

## 两个被普遍误解的点

**1. 签名 ≠ 没有警告**

OV 证书对 SmartScreen 的信任是累积的：新证书刚签发时，其签署的文件依然会被拦截，需靠下载量逐步建立声誉。只有 EV 证书能立即获得信任。因此「花钱签名 = 用户双击即装」的假设不成立。

**2. 自签名是负收益**

自签名证书不在 Windows 受信任根列表中，文件签名会被判定为「不受信任」。用户看到的是比「未知发布者」更严重的警告。若要求用户手动导入根证书来解决，等于训练用户接受未知证书，安全成本远高于收益。

## 现行做法

1. Release 中公布每个文件的 SHA-256，安装前可校验
2. README 与 Release 说明中如实写明未签名，并给出跳过 SmartScreen 的操作步骤
3. README 的 Code signing policy 段落描述真实状态，不再声明正在申请

## 重新评估的触发条件

满足任一条再启动评估：

- 项目 star 数达到数百，或有外部文章/视频提及
- 分发对象从公会内测扩展到公网玩家
- 出现集中的用户投诉，明确指向 SmartScreen 提示阻碍安装

届时优先顺序：Microsoft Store（一次性 $19）> Certum OV（¥230/年）> EV（¥2000+/年）。

## 提升公开信号的低成本做法

这些事对项目本身有独立价值，不是为审核而做：

1. 仓库补充界面截图、issue 模板、CONTRIBUTING
2. 写技术文章：基于 Theseus 做定制启动器的实践
3. 发布到中文 MC 社区与视频平台
4. 让真实用户点 star —— 不刷量，刷量会毁掉可信度
